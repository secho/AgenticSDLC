The Method

Ten thousand procedures nobody dares to touch

Every large company has a core it is afraid of. Code that has been accreting for fifteen years, written by people who have left, with no documentation and no tests. The usual advice is a multi-year modernisation programme. There is a faster route, and it starts somewhere unexpected: not with rewriting anything, but with working out what you are able to prove.

00 the pivot

You don't need to know what it should do

The reason legacy modernisation is slow is not that the code is hard to read. It is that nobody can say whether a rewrite is correct. There is no specification to check against — the specification left the company in 2016.

The pivot that makes the whole thing tractable is this: when you are modernising, you don't need to know what the code should do. You only need to know what it did. Correctness stops meaning "matches the intent" and starts meaning "behaves exactly as it behaved yesterday". And that is knowable, because the old code is running in production right now and can be watched.

Everything below follows from that one move.

01 triage

Sort by what you can prove, not by what looks hard

The first pass over the estate does not read for meaning. It reads for verifiability: for each procedure, what kind of evidence could ever tell you that a replacement behaves the same?

Four answers, and they are properties of the code, not opinions about it. Does it only read? Does it write, but deterministically? Does its result depend on the clock, on generated identifiers, on unstable ordering? Does it call something outside the database?

pure read
returns data, writes nothing. The easy case.
deterministic write
same inputs, same writes. Verifiable with effort.
non-deterministic
depends on time, generated IDs, or ordering. Needs a seam before anything else is possible.
external effect
reaches outside the database. Cannot be replayed safely.

This is the pass that no human does across ten thousand procedures, and it is the one that decides everything afterwards — because a procedure's class determines how much autonomy an agent can ever be given over it.

02 spec

Make it legible before you make it different

An agent reads the procedure and writes down what it does, in plain language: purpose, inputs, behaviour branch by branch, the invariants that appear to hold, which tables and columns it touches — and, most valuably, the open questions. The behaviour it cannot tell is intentional from the behaviour that looks like a mistake.

Nothing has changed yet. But for the first time the whole estate is readable at once, rather than only where somebody has time to look.

Morgan Stanley did exactly this at scale in 2025: their internal tool read roughly nine million lines of legacy code and translated it into plain-English specifications, which the company estimated saved around 280,000 developer hours. Not a rewrite. A translation, so that a rewrite became possible.

03 oracle

The word for the thing that tells you it's right

A test is two parts: an input, and something that decides whether the answer is correct. That second part is called an oracle, and it is the expensive half. Anyone can invent inputs.

An agent can write a replacement procedure in a minute. It cannot tell you whether you may deploy it. Only an oracle can. This is why raw code-generation speed changes so little on its own: generation was never the bottleneck. Judgement was.

For legacy code the oracle is built from what the system already does. Every call in production is recorded — inputs, results, and the full set of rows it wrote. Those recordings become test cases. Not invented cases: real ones, in real proportions, including the situations nobody would have thought to write down.

The bookkeeper

A bookkeeper of fifteen years is leaving. She calculates commissions by rules that were never written down. You don't ask the new hire whether she can do it — you have her work in parallel for a month and compare the numbers. That parallel run is the oracle. You never needed the rules. You needed a reference and a way to compare.

04 baseline shadow run

Prove the harness before you trust the verdict

Before replacing anything, the recorded calls are replayed against the existing procedure — the one already in production.

This sounds redundant and is the step most often skipped. Its purpose is to prove the machinery itself is sound: that replay reproduces reality, that the clock and generated identifiers are properly pinned, that ordering is normalised, that the comparison is not producing noise of its own.

If the old code cannot be shown to match itself, no verdict about new code means anything.

05 diff classification

Thousands of differences, twelve that matter

Replaying production traffic produces a lot of differences, and most of them mean nothing: a timestamp, a generated identifier, two rows that came back in a different order, a floating-point tail.

Mechanical normalisation removes what it can. Whatever survives goes to an agent that labels it noise — with a stated reason — or a real change in behaviour, with an explanation of what changed and what it would mean for the business.

This step is the reason the method scales. Without it you have not removed the bottleneck, you have moved it: from writing code to reading diffs. With it, a person sees only the handful that genuinely need a human.

06 implement

Now, and only now, write the replacement

With a specification, a test suite drawn from real traffic, invariants, and a comparison harness proven against itself, writing the replacement is the least interesting step. It is also the first step at which the code actually changes.

One rule dominates everything here: preserve behaviour, do not fix bugs. The specification's open questions will contain things that look wrong, and some of them are wrong. Reproduce them anyway. A behavioural fix bundled into a migration makes the comparison unreadable — nobody can tell whether the new code is broken or better. Fixes come afterwards, as their own change, with their own evidence.

07 verdict shadow run

The new code runs dry, next to the real thing

The same recorded calls now replay against the replacement. The customer only ever sees the old procedure's answer; the new one runs alongside inside a transaction that is always rolled back. Production is never touched.

Both the returned result and the full set of intended writes are compared. Matches accumulate. Real differences go to the queue.

And here is the part worth pausing on: the differences that reach a human are frequently not defects in the new code. They are things the old code has been doing for years that nobody knew about. The system finds them — and does not quietly fix them. It asks.

The limits

Where it stops

A method that claims no limits should not be believed.

Knowledge that was never written down is gone. If a rule lived only in the head of someone who has left, an agent can read from the code what happens. It cannot read whether that was the intention. The difference between a bug and a feature in fifteen-year-old code is not a question a model can settle.

Some changes are irreversible and unverifiable at the same time. Schema migrations on the core, anything with accounting or regulatory consequences. These stay with people — not because the model is not capable, but because the cost of being wrong is wildly out of proportion to what automation saves.

Some code has no oracle at all. A score computed by rules accreted over a decade, where the correct answer is by definition whatever the current code returns, can be shown to be equivalent — but the moment you want to change it, there is nothing to measure against. Plan for people there. Do not wait for it to solve itself.

The close

The metric that actually matters

Not procedures migrated. How often a human has to step in.

When that number falls, the boundary of what agents may do on their own moves outward, and debt repayment becomes a by-product rather than a programme. It is also the honest measure of whether any of this is working — a system that needs constant correction is telling you its instructions are wrong, not that the model is weak.
