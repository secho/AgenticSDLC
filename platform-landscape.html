Market Landscape

The AI SDLC platform landscape

Every major dev-tools vendor has shipped some version of "agents that write and ship code" in the last eighteen months. Before you architect your own agentic SDLC, it helps to know what the market already sells — where it's strong, where it locks you in, and where the gaps are that a vendor-agnostic architecture fills.

Two halves below. First the agents and the control planes that govern them — the part of the market that gets the attention. Then the layers underneath: the model gateway, the sandbox, the observability plane, the review and verification tier. Those are the pieces that decide whether the agent on top is actually replaceable.

Platform Profiles

Three groups, doing different jobs. Governance layers manage agents they don't provide. Autonomous coding agents do the work. IDE-native and ecosystem assistants keep a human in the loop. Most real stacks end up combining one from each.

Governance & orchestration

These don't write code themselves — they sit above the agents that do, adding the context, policy, identity, and cost control an organization needs before it lets agents loose at scale.

JetBrains Central

Governance layer · Model-agnostic

Not an IDE or a model — an orchestration and governance layer that sits above whichever agents a team already runs (Claude Agent, Codex, Gemini CLI, or custom). It adds policy enforcement, identity, cost attribution, and cloud execution infrastructure across the tools a team already uses, and lets agents collaborate with humans through Slack, Atlassian, and Linear. JetBrains frames it around a survey finding it published in early 2026: ~90% of developers use AI, but only ~22% use coding agents — the bottleneck has moved from generating code to governing it. It manages agents; it doesn't replace the need to select and pay for them separately.

  • PricingShifting to on-demand AI credits; Early Access Program in Q2 2026
  • BackingFrom JetBrains (IntelliJ, PyCharm); launch partners Google Cloud, Anthropic, OpenAI
  • Best forGoverning policy and cost across many agents, models, and clouds
  • Watch forEarly — limited rollout through 2026, not yet generally available

Port.io

Agentic engineering platform (IDP) · Model-agnostic

An internal developer portal that repositioned in 2026 as an agentic engineering platform. Rather than ship its own coding agent, it becomes the control plane: a Context Lake (a pre-joined catalog of services, ownership, and standards) that agents query, workflow orchestration, an AI Registry cataloguing every agent, skill, and MCP server in the org, and governance that scopes what each agent can read and do via RBAC. Claude, Cursor, and Copilot reach it through Port's MCP server. Its pitch is taming "agentic chaos" — and cost: Port reports its Context Lake cut per-query token spend 56–80% versus agents hitting raw MCP connections, by not re-deriving system relationships on every run.

  • PricingFree tier; Basic $30 and Standard $40 per seat/mo; custom Enterprise
  • Backing~$158M raised, ~$800M valuation (Series C led by General Atlantic, late 2025)
  • Best forPlatform teams unifying agent context, catalog, and governance on an IDP
  • Watch forA control plane, not a coding agent — you still bring the agents

Autonomous coding agents

These do the actual work — plan a task, execute it in a sandbox, and hand back a pull request. They range from fully unattended to human-supervised.

Factory.ai

Multi-surface Droids · Model-agnostic

Organizes agents by job function rather than shipping one general-purpose assistant — a Code Droid ships changes, a Reliability Droid investigates incidents, a Knowledge Droid writes docs, a Product Droid drafts PRDs. They run from a terminal, desktop app, SDK, or headless in CI/CD, and work against any leading frontier or open-weight model. Factory commits to not training on customer code and operates under SOC 2 Type II. Its broad "run agents across the whole delivery workflow" framing is the ambition; the caveat is cost predictability under heavy use.

  • PricingPro $20, Plus $100, Max $200 per month; Enterprise on request
  • Traction~$1.5B valuation; used at Nvidia, Adobe, Morgan Stanley, MongoDB; ranked #1 on Terminal-Bench
  • Best forTeams wanting agents across the full delivery workflow, not just editing
  • Watch forUsage costs can balloon on heavy autonomous workloads

Devin (Cognition)

Autonomous coding agent · Cognition

Popularized the "assign it a ticket" model: it plans, executes inside an isolated VM with its own browser, terminal, and editor, and opens a PR with no supervision during the run — several tickets in parallel, each in its own sandbox. Pricing moved from a flat $500/seat to usage-based billing (ACUs, a normalized measure of VM time and inference), which drove rapid growth. Cognition also acquired the Windsurf IDE. Independent testing consistently puts real-world success rates well below its benchmark headline, so budget review time on anything non-trivial.

  • PricingUsage-based (ACUs); tiers from free up to ~$500/mo Team, plus Enterprise
  • TractionCognition valued ~$26B; Nubank ran a 6M-line migration on it, citing large efficiency gains
  • Best forParallel, well-scoped ticket backlogs and large-scale migrations
  • Watch forReal-world success trails the benchmark headline — review overhead is real

GitHub Copilot — Agent Mode & Coding Agent

In-editor + async cloud agent · Multi-model

Two tiers span the workflow. Agent Mode makes supervised multi-file edits inside the IDE (VS Code, Visual Studio, JetBrains, Eclipse, Xcode); the separate Coding Agent takes a GitHub Issue and returns a PR asynchronously from a GitHub Actions sandbox. Every PR the Coding Agent opens triggers CodeQL, secret scanning, and Dependabot automatically, and MCP lets it pull context from databases, Confluence, or Figma mid-task. The tradeoff is ecosystem gravity — it assumes GitHub as the system of record — and a known gap: .copilotignore exclusions don't apply to the Coding Agent.

  • PricingFree; Pro $10, Pro+ $39, Business $19, Enterprise $39; usage-based for agentic features
  • Traction~20M users, ~4.7M paid; the coding agent is used across ~90% of the Fortune 100
  • Best forTeams standardized on GitHub as their system of record
  • Watch forEcosystem lock-in; ignore-file exclusions don't bind the Coding Agent

Anthropic Claude Code

Terminal/IDE agent + enterprise platform · Claude only

Started as a terminal coding assistant and grew an enterprise layer on top: Dynamic Workflows fan a single request out to dozens or hundreds of parallel sub-agents for codebase-scale refactors and migrations; Managed Agents provide hosted infrastructure for stateful, long-running agents so teams don't build the execution loop themselves; an open Skills standard and plugin marketplace let orgs package and deploy reusable capabilities; and admin controls add spend caps, analytics, and model routing — much of what JetBrains Central and Port aim to standardize across vendors, but for Claude specifically. Deployable on Anthropic's cloud, Azure, or self-hosted, with a US data zone for residency.

  • PricingVia Claude Pro/Max subscriptions and API; enterprise spend caps and analytics
  • StrengthsParallel sub-agents, Managed Agents, Skills standard, plugin marketplace
  • Best forDeep interactive engineering and codebase-scale refactors/migrations
  • Watch forClaude-only — no choice of underlying model

Google Jules

Async coding agent · Gemini only

Built for fire-and-forget review: no editor, no local mode — everything clones into a Google Cloud VM, where Jules drafts a plan, executes, adds tests alongside the implementation, and opens a PR. Strong on scoped, well-defined tasks; weaker on architectural judgment and large-codebase context, matching its reputation as a capable junior developer that still needs oversight. Teams often pair it with an interactive tool — Jules for long-running or overnight work, something like Claude Code or Cursor for the in-the-loop engineering.

  • PricingFree (15 tasks/day); AI Pro $19.99 and AI Ultra $124.99 per month by task quota
  • Runs onGemini, inside a Google Cloud VM — no local or editor surface
  • Best forFire-and-forget PRs on routine, well-scoped tasks
  • Watch forWeak on complex/architectural work; execution is Google-Cloud-only

OpenAI Codex

CLI + cloud coding agent · GPT-5.x-Codex

Covers the same asynchronous issue-to-PR pattern as Jules, but spans the terminal, the ChatGPT app, and the cloud, routing over coding-specific GPT-5.x variants. Its differentiator is an open-source CLI (Apache-2.0) that teams can audit and run locally — useful where the cloud agents' code upload or Jules' Google-VM-only model is a non-starter on data residency. Switch to the local CLI when you need strict control; use the cloud when you want fire-and-forget.

  • PricingBundled with paid ChatGPT plans; API-rate billing for overflow usage
  • SurfacesOpen-source CLI (Apache-2.0), ChatGPT app, and OpenAI cloud
  • Best forTeams wanting an auditable, self-hostable CLI alongside cloud PRs
  • Watch forCloud agents upload code to OpenAI — use the CLI for strict control

IDE-native & ecosystem-specific assistants

These keep a developer in the driver's seat — agentic help delivered inside an editor or tied to a specific ecosystem, rather than run unattended.

Cursor

AI-native IDE · Multiple models

An IDE first — a VS Code fork with agentic editing built in rather than bolted on: Composer for multi-file changes, Rules/Commands for repeatable behavior, and background cloud agents for parallel work. It embeds code chunks for retrieval (a RAG approach to codebase context) and lets developers pick the underlying model. The fastest path for someone who wants high-autonomy editing without leaving a familiar editor shell, but tuned for solo and small-team speed rather than org-wide governance.

  • PricingSubscription IDE with per-tier request limits; multiple selectable models
  • StrengthsComposer multi-file edits, background cloud agents, multi-agent workflows
  • Best forFast, high-autonomy in-editor work for individuals and small teams
  • Watch forOptimized for editing speed over organization-wide governance

Amazon Q Developer

Cloud-native assistant · Amazon Bedrock

An AWS modernization accelerator more than a general coding agent — built on Amazon Bedrock, IAM-aware, and integrated across IDEs and the AWS Console with chat in Slack and Teams. It's strongest on tasks tied to AWS infrastructure: migrations, modernization, and console automation. Analysts frame it as complementary to editor-native tools rather than a replacement — the AWS operations layer alongside your IDE. Off an AWS-centric stack, the model-agnostic options on this list are a stronger general-purpose choice.

  • PricingFree tier plus paid Pro; part of the AWS ecosystem
  • Runs onAmazon Bedrock, IAM-aware, across major IDEs and the AWS Console
  • Best forAWS-native modernization, migrations, and console-driven tasks
  • Watch forWeaker general-purpose choice off an AWS-centric stack

Sourcegraph Cody & Amp

Search-backed assistant + agent · Enterprise LLMs / model-agnostic

Sourcegraph split its offering in two. Cody leans on Sourcegraph's code-search graph — a structural advantage in sprawling, multi-repo estates — but went enterprise-only in 2025 (its free and pro tiers were retired), lags newer tools on raw agentic capability, and can be slow on multi-million-line monorepos. Amp is the separate, more agentic product: model-agnostic routing, multi-agent orchestration, shared team threads, and zero-data-retention deployment for compliance-sensitive teams. Many orgs keep Sourcegraph for search and pair it with a separate agent for execution.

  • PricingCody enterprise-only (free/pro retired 2025); Amp sold separately
  • StrengthsCody = code-search-graph context; Amp = model-agnostic multi-agent + ZDR
  • Best forMassive multi-repo estates where finding code is the real bottleneck
  • Watch forCody lags on agentic depth; latency on very large monorepos
The Layers Underneath

Everything above competes for the same slot: the thing that writes the code. But an agent is only the visible layer of a stack. Underneath it sits a model gateway deciding which LLM answers and what it costs; a sandbox where generated code actually runs; an observability plane recording what happened; and a review tier that decides whether any of it ships.

These get bought later, usually after the first agent rollout has already made them urgent — and by then the decision has often been made by default. That matters, because this is where replaceability is actually won or lost. An agent you can swap is worth little if its model routing, execution, and audit trail are welded to one vendor. Put a gateway underneath and the model layer becomes a config change; skip it and every agent negotiates its own billing relationship with every provider.

Model gateways & routing

One endpoint in front of every model provider. Agents point at it instead of at OpenAI or Anthropic directly, and it becomes the single place you enforce budgets, keys, fallback, and audit — the layer that makes "swap the model" a config change rather than a migration.

LiteLLM

Open-source AI gateway · BerriAI

The default open-source answer to "how do we stop every team wiring their own provider keys". A proxy that exposes 100+ providers — Bedrock, Azure, Vertex, Anthropic, OpenAI, vLLM, NVIDIA NIM — behind one OpenAI-compatible endpoint, with per-key and per-team budgets, model allowlists, rate limits, secret redaction, and spend tracking on every call. The part that matters for an agentic SDLC: the coding agents already speak to it. Claude Code points at a gateway with two environment variables (ANTHROPIC_BASE_URL and ANTHROPIC_AUTH_TOKEN), and Codex, Gemini CLI, Roo Code and others route the same way — so one proxy gives you attributed, budget-capped, auditable spend across every agent in the org, including per-session and per-sub-agent breakdown from the headers Claude Code sends. It added an MCP gateway front door in August 2026, putting tool access behind the same control point as model access. It is infrastructure you operate, which is the tradeoff: below roughly $2K/month of inference the running cost outweighs the saving, and above ~$10K/month it is usually the cheapest option on this page.

  • PricingFree to self-host (MIT core); Enterprise from ~$250/mo, sized to request capacity — never per token
  • EnterpriseSSO/SAML, audit logs, RBAC, KMS/Vault integration, air-gapped deployment, 24/7 SLA
  • Traction~54K GitHub stars, 1,000+ contributors; in production at Netflix, Lemonade, Rocket Money
  • Best forMaking the model layer swappable and putting one budget and audit trail under every agent
  • Watch forYou operate it — needs DevOps capacity, and it becomes a availability-critical hop

Bifrost

Open-source AI gateway · Maxim AI

The same architectural idea as LiteLLM, rebuilt in Go and aimed squarely at it. Apache 2.0, ships as a single binary (Docker, Kubernetes, or npx), and covers 23+ providers and 1,000+ models with drop-in compatibility for the OpenAI, Anthropic, Bedrock and Google GenAI SDKs — so the same two-environment-variable trick that points a coding agent at a gateway works here too. Governance is comparable: virtual keys, hierarchical budgets, rate limits, plus OIDC/OAuth 2.0 with directory sync for teams and roles. What it bundles that LiteLLM leaves to you: native cluster mode, semantic caching, guardrails, and Prometheus metrics and tracing without an external dependency.

Its marketing leads on being "50x faster than LiteLLM". That claim is more defensible than most vendor benchmarks — the suite is open source and third parties have reproduced similar magnitudes — and it is also mostly irrelevant to the workload this site is about. We take it apart below.

  • PricingFree and open source (Apache 2.0); enterprise tier adds private deployment, adaptive load balancing, custom security
  • Traction~7.4K GitHub stars, ~1.1K forks — young relative to LiteLLM, fewer named production references
  • Best forHigh-throughput inference where gateway overhead is a real cost, or teams who would rather not operate a Python service
  • Watch forNarrower provider coverage and a single-vendor project — weigh that against the engineering

OpenRouter

Hosted model marketplace · Aggregator

The zero-effort version of the same idea: one API key, 400+ models, routing and fallback handled for you. It removes the operational burden LiteLLM imposes, and in exchange you accept a hosted intermediary in the path of every inference call and roughly a 5% margin on top of provider pricing. Excellent for evaluation and for teams who want to try six models this month without six procurement conversations; harder to justify once spend is material or once inference has to stay inside your own network.

  • PricingPay-per-use at provider rates plus roughly 5%
  • Traction~$1.3B valuation (Series B led by CapitalG, May 2026); ~25T tokens/week across 400+ models
  • Best forFast model evaluation and breadth without running infrastructure
  • Watch forA third party sits in every request path — check that against your data policy

Portkey

Managed AI gateway + guardrails · Hybrid open source

Sits between the two: an open-source gateway core with a managed control plane focused on what happens after you deploy — observability, retries, caching, and a library of 50+ guardrails applied inline on requests and responses. Deployable into a customer VPC, which is the usual reason it wins over OpenRouter in regulated environments. The catch is packaging: the governance features that justify a gateway in the first place — RBAC, per-team budgets, SSO, custom retention — sit behind the Enterprise tier.

  • PricingFree Developer tier; Production ~$49/mo; Enterprise custom (SSO, VPC, RBAC, HIPAA/SOC 2)
  • Traction$15M Series A (Elevation Capital, Feb 2026); ~14B tokens/day processed
  • Best forTeams wanting gateway plus guardrails and tracing without operating the stack
  • Watch forGovernance is gated to Enterprise — price it in before you compare to LiteLLM

Execution sandboxes

Every autonomous agent above runs code it just wrote. Bundled platforms hide this behind their own cloud; if you want agents on your infrastructure, this is the layer you buy or build.

E2B

Firecracker microVM sandboxes · Open source

Hardware-level isolation for untrusted, model-generated code — each execution gets its own kernel via Firecracker, the same microVM technology under AWS Lambda, so a kernel-level exploit can't reach the host or a neighbouring run. That distinction matters more than it sounds: container-based sandboxes share the host kernel, which is an acceptable risk for your own code and a harder argument for code an LLM wrote unsupervised. Open source and self-hostable, which keeps the execution layer under your control rather than the agent vendor's.

  • IsolationFirecracker microVMs — dedicated kernel per execution
  • TractionReports use at ~94% of the Fortune 100; 1B+ sandboxes started, ~3.5M monthly SDK downloads
  • Best forRunning agent-written code where the isolation boundary has to hold
  • Watch formicroVM start-up is slower than containers — the price of the stronger boundary

Daytona

Stateful container workspaces · Managed

Optimized for the other end of the tradeoff: container-based workspaces with roughly 90 ms cold starts — the fastest in 2026 third-party benchmarks — and persistent state, so an agent can install dependencies, write files, and return to the same environment on a later turn. That statefulness fits long-running agent sessions well. The significant change is governance, not technology: the codebase went closed-source in mid-2026, so full self-hosting is no longer available, and the isolation boundary is a shared host kernel.

  • IsolationContainers — shared host kernel, weaker boundary than a microVM
  • Strengths~90 ms cold start; stateful workspaces that survive across agent turns
  • Best forLatency-sensitive, long-lived agent sessions on trusted-ish code
  • Watch forClosed-source since mid-2026 — managed-only, so it is a dependency, not a component

Observability & evaluation

You cannot govern what you cannot see, and you cannot tell whether a prompt or model change improved anything without a scoring harness. This layer is what turns "the agents seem better" into a number.

Langfuse

Open-source LLM observability · MIT

The open-source baseline: tracing across multi-turn agent runs, prompt versioning with a playground, and evaluation via LLM-as-judge, human feedback, or custom metrics. MIT-licensed with self-hosting as a first-class deployment mode rather than an enterprise upsell — which is the whole argument for it in regulated environments, since traces of agent runs over your source code are exactly the data you least want leaving the building. LiteLLM can route its per-team logs straight into it, making the two a common pairing.

  • PricingFree self-hosted (MIT); managed cloud from ~$29/mo
  • Traction~28K GitHub stars; the most-adopted open-source option in the category
  • Best forKeeping agent traces inside your own perimeter with no licence gate on self-hosting
  • Watch forSelf-hosting means you own the storage and retention problem too

LangSmith & Braintrust

Managed tracing / evaluation-first · Proprietary

LangSmith is LangChain's managed surface — strongest if you already build on LangChain, and it shipped a purpose-built trace store (SmithDB) in 2026 for materially faster queries at volume. Its constraint is structural: the SDKs are open source but the backend, UI, and storage are not, and self-hosting is an Enterprise-only add-on. Braintrust attacks the harder half — rigorous evaluation, with datasets, scorers, and regression tracking as the primary object rather than tracing bolted onto it. If your problem is "did this change make the agent better", that focus is the point; it is also the most vendor-hosted option here.

  • PricingLangSmith: free tier, ~$39/seat/mo Plus, custom Enterprise. Braintrust: free tier up to ~$249/mo Pro
  • TractionBraintrust raised $80M Series B at ~$800M valuation (Feb 2026)
  • Best forLangSmith on a LangChain stack; Braintrust where eval rigour is the actual requirement
  • Watch forBoth are proprietary — LangSmith self-hosting is Enterprise-gated, Braintrust is cloud-only

Automated review & verification

Once agents open pull requests faster than people can read them, review becomes the bottleneck. This layer is the direct answer — and it is the commercial version of the argument on The Method: generating code was never the constraint, judging it was.

CodeRabbit

AI pull-request review · SaaS + self-hosted

The most widely installed review agent on GitHub and GitLab — over 2M repositories connected and 13M+ pull requests processed — which matters here mostly as evidence of how quickly this became a real category. It comments line-by-line on every PR, and in comparative testing it flags fewer issues than the most aggressive alternatives but wastes markedly less reviewer time on false positives. Given that the failure mode of automated review is reviewers learning to ignore it, that ratio is the metric to judge on, not raw catch rate.

  • PricingFree tier for summaries; Pro ~$24–30/user/mo; Enterprise adds self-hosting
  • Traction$60M Series B at ~$550M valuation (Sept 2025); 2M+ repos, 13M+ PRs reviewed
  • Best forBroad first-pass review coverage where signal-to-noise decides adoption
  • Watch forPer-seat pricing scales with the team, not with how many PRs agents actually open

Greptile

Codebase-aware review · SaaS

Reviews a change against the whole repository rather than the diff in isolation, which is why it is the stronger of the two at architectural impact — the "this is fine locally and wrong for this system" class of problem that a diff-scoped reviewer structurally cannot see. It also catches the most issues per pass in comparative testing, and generates the most false positives doing it. Whether that trade works depends entirely on whether your reviewers still read the output after two weeks.

  • PricingFree Starter tier (June 2026); Pro ~$30/seat/mo with review credits; free for public OSS
  • TractionSeries A led by Benchmark at ~$180M valuation (2026)
  • Best forLarge codebases where the expensive defects are architectural, not local
  • Watch forHighest false-positive rate in the category — tune it or lose the reviewers

Deterministic modernization

The non-probabilistic counterpart to everything above — and the right tool for a large share of legacy work that teams reflexively hand to an LLM.

Moderne & OpenRewrite

Rule-based mass refactoring · Open-source engine + enterprise platform

OpenRewrite is an open-source refactoring engine built on a Lossless Semantic Tree — a code model that resolves symbols, tracks relationships, and preserves formatting and intent, so a transformation either applies correctly or does not apply at all. Moderne is the enterprise platform that runs those recipes across thousands of repositories at once, with an audit trail. Java-first, with Python support added in early 2026.

The reason it belongs on this page: for framework upgrades, API migrations, and CVE remediation, a deterministic recipe is strictly better than an agent — it needs no review budget, no shadow run, and no oracle, because it cannot produce a surprise. The honest architecture uses both: recipes for anything expressible as a rule, agents for the work that genuinely requires judgement. Reaching for an LLM first on mechanical refactoring is the most common expensive mistake in this space.

  • PricingOpenRewrite free and open source; Moderne platform commercial
  • Traction$30M Series B; in use at Walmart and Allstate, and inside AWS and Microsoft tooling
  • Best forAnything expressible as a rule — upgrades, API migrations, vulnerability remediation at scale
  • Watch forRequires a recipe to exist or be written; no help where behaviour must be inferred

The benchmark question

Bifrost's headline is that it is 50× faster than LiteLLM. The underlying figures are more specific than the headline, and the difference between them matters:

  • 50×throughput at sustained load
  • 9.5×median latency
  • 54×P99 latency
  • 68%less memory
  • 11 µsadded overhead at 5,000 requests/second

Credit where it is due: Maxim open-sourced the benchmark suite, third parties have reproduced results of similar magnitude, and the architectural explanation is sound — compiled Go against CPython has measurably less per-request overhead on a hot path. This is better practice than most vendor benchmarking. The place to be careful is the headline: quoting the throughput multiplier as if it were a latency multiplier is where a legitimate measurement becomes marketing.

The more useful objection is about relevance. The benchmarks use mocked provider endpoints, which is the correct way to isolate gateway overhead — and also the configuration that maximises the visible gap, because it removes the provider latency that dominates every real request. Do the arithmetic for an agentic workload:

frontier completion for a coding agent  ≈  2,000–20,000 ms
gateway overhead, Bifrost  ≈  0.011 ms
gateway overhead, LiteLLM  ≈  1 ms  (generous, ~90× worse)
difference in what a developer perceives  ≈  0.005%

A 50× faster gateway makes no difference a developer or an agent can feel, because the gateway was never the slow part. Choosing on this number is the same error the Eye Cycle flags as terminal for agent selection: optimising a benchmark that does not match the workload.

Where the difference is real

It would be wrong to conclude the engineering does not matter. It matters in three specific regimes, and if you are in one of them the calculus inverts.

Sustained high request rates. At thousands of requests per second the gateway's own CPU and memory become a line item. 68% less memory and an order of magnitude more throughput per instance is real infrastructure cost, and it compounds. Note the scale, though: 5,000 requests/second is roughly 430 million calls a day. That is a consumer AI product, not an estate governing three hundred developers' agents.

Tail latency under load. The P99 gap is the number worth attention, and not because of speed — because it indicates queuing. A gateway that degrades badly at its ceiling turns into an availability problem for every AI workflow behind it, which is the one failure mode that actually hurts. If your traffic is spiky, headroom is worth buying.

Operating a Python service versus a binary. This is the underrated one. A single static binary with native clustering, metrics and caching has a materially smaller operational surface than a Python service plus Redis plus an external observability stack plus dependency management. For whoever carries the pager, that is a genuine difference, and it does not appear in any benchmark.

Where LiteLLM still wins

Provider coverage, by a wide margin. 100+ against 23+. In a heterogeneous enterprise estate — a legacy Azure OpenAI deployment here, Bedrock there, a self-hosted vLLM cluster for a data-residency edge case, someone's Cohere contract — breadth is the feature that decides whether the gateway can actually sit in front of everything. A gateway that covers most of your traffic is not a control point.

Ecosystem gravity. Roughly seven times the stars and over a thousand contributors is not a vanity metric here; it is the probability that the integration you need already exists, that your problem is already an answered issue, and that the project outlives any single company's strategy. Bifrost is well engineered and stewarded by one vendor. Weigh that the way you would weigh it for any other dependency.

Track record under load you can point at. Named production deployments at Netflix, Lemonade and Rocket Money are evidence of a kind that benchmarks are not.

How we would choose

Default to LiteLLM for a governance and attribution control plane in a mixed enterprise estate. Provider breadth and ecosystem maturity are the properties that determine whether the gateway can be the single place every call passes through, and that is the whole point of installing one. Gateway overhead is noise at this scale.

Choose Bifrost if you are serving sustained high-volume inference where per-request overhead is a real cost, if spiky traffic makes tail-latency headroom worth paying for, or if avoiding a Python runtime and its dependency surface materially simplifies who can operate it.

Do not migrate on the benchmark alone. Both expose an OpenAI-compatible surface, so moving between them is genuinely cheap — which is an argument for deciding on coverage and operations now, and revisiting on evidence from your own traffic rather than someone else's test harness.

The Secho Quadrant

Analyst quadrants usually plot capability against vision, which tells you who is winning and nothing about what you are signing up for. This one plots the two things an engineering leader actually has to trade off.

Horizontal — independence: how cheaply you could replace this in eighteen months. Open source, self-hostable, standard protocols and portable artifacts move a platform right. Proprietary execution, a required cloud, a single model vendor, or a proprietary system of record move it left.

Vertical — surface area: how much of the delivery lifecycle it owns. High is not better. A platform high on this axis does more for you and displaces more of your architecture; one low on it does a single job and gets out of the way.

Reading it

Gravity wells are the most capable products on the page and the most expensive to leave. Claude Code, Copilot, Devin, Cursor and Codex all deliver real autonomy today, and each one assumes something structural in return — a single model vendor, GitHub as the system of record, vendor-hosted execution, a specific editor. None of that is a reason to avoid them. It is a reason to know which assumption you are accepting, and to keep the layers underneath them yours.

Load-bearing is the small set that does a lot without dictating much: Factory.ai, because it is model-agnostic and runs headless in your own CI; Port.io, because it governs agents it does not supply; Sourcegraph Amp, for model-agnostic routing with zero-data-retention deployment. This is the quadrant to prefer for anything you expect to still be running in three years.

Swappable parts is where most of the infrastructure sits, and low surface area is the feature. LiteLLM, Bifrost, Langfuse, E2B and OpenRewrite each do one job, are open source, and cost roughly a day to remove. Bifrost sits marginally left of LiteLLM on independence for one reason that has nothing to do with its licence, which is more permissive: it is stewarded by a single vendor, where LiteLLM has a thousand contributors. That is the same consideration you would apply to any other dependency. JetBrains Central sits here rather than in load-bearing for one reason only: it is not generally available yet. Delivered scope is what the vertical axis measures, and an early-access product has not delivered it.

Ecosystem bets is the quadrant that needs the most honesty. Google Jules and Amazon Q are genuinely good inside Google Cloud and AWS respectively and weak outside them — correct choices if that commitment is already made, poor ones as a hedge. Daytona and the proprietary observability tools land here on packaging rather than capability: a managed-only sandbox and an Enterprise-gated trace store are fine products that you cannot take with you.

The diagonal is the actual finding. Almost nothing sits in the top-right. The market has not yet produced a platform that does most of the lifecycle without owning most of your architecture — which is precisely why the working pattern is a load-bearing or gravity-well agent on top, with independent, swappable layers underneath.

Secho's Eye Cycle

The quadrant is about vendors. This is about techniques — the things that stay true after the logos change. A vendor can be excellent while the technique it sells is still a few months from being usable, and the reverse happens just as often: the least fashionable idea on this curve is frequently the one that pays.

Five phases: first contact (it exists, mostly in papers and demos), overclaim (the conference-talk peak), reckoning (production contact), real practice (people who ship start writing down what works), and load-bearing (boring, assumed, invisible).

The horizon is months, not years. Analyst hype cycles are calibrated to enterprise software timescales, where five years to the plateau is normal. That calibration is wrong here. This field re-tools roughly every quarter, so the marker against each technique below is months to load-bearing — the point at which you would stop treating it as a bet and start assuming it. Plan procurement and hiring against that clock, not a five-year one.

The calls worth arguing about

The genuinely new work is on the far left, and it is about proof, not generation (1–3). Learned world-models of a codebase, proof-carrying agent output, and auto-formalisation of legacy code into machine-checkable specifications are all early — papers, prototypes, and internal experiments. They share a direction that is worth noticing: every one attacks verification rather than authorship. That is the tell for where the field's remaining hard problems actually are, and it is why these are the ones to watch even though none is deployable today.

Continuous shadow production (4) is the sleeper. Shadow running is currently framed as a migration technique — you stand it up, you cut over, you tear it down. The interesting move is to never tear it down: keep a permanent parallel-run of the service so every change, human or agent, is differentially compared against the incumbent before promotion. That converts verification from a project into infrastructure, and it is the single change that would most widen what agents can be trusted to do unsupervised.

Fully unattended ticket-to-PR (12) is over the peak, not through it. The capability is real and the demos are honest; what has not held is the economics at organizational scale. Independent evaluation keeps landing well below benchmark headlines, and the cost that matters is not inference — it is senior review time spent on plausible-looking output. It arrives, but as a governed subset of tickets rather than the default intake path.

Benchmark-led agent selection (15) will not recover. Choosing tools by SWE-bench-style scores is being abandoned rather than improved: the benchmarks are saturated, contaminated, and measure a task shape that does not match legacy estates. What replaces it is not a better benchmark — it is evaluation on your own code, which is technique 21, and it is why that one is nearly load-bearing.

Shadow-run verification (20) is the most under-rated position on this curve. It never had a peak because it is unglamorous, and it is the closest thing the field has to a solved problem: replay recorded production traffic against old and new implementations and compare. It is the mechanism behind The Method, and the reason it matters more than any generation technique is arithmetic — generation stopped being the constraint some time ago, and judgement never did.

Deterministic rule-based refactoring (26) has been load-bearing the whole time. It is the technique most often skipped because it predates the current cycle and does not involve a model. For everything expressible as a rule, it beats an agent outright: no review budget, no verification harness, no possibility of surprise. The mature stack uses recipes where a rule fits and reserves agents for work that actually needs judgement.

Placement is a judgment call about techniques, not a survey. The useful way to read it: things on the right are safe to depend on, things at the peak deserve a bounded pilot rather than a programme, and things in the reckoning phase are where budget quietly disappears. The months are deliberately short — a technique two months from load-bearing is one you should be staffing for now, not scheduling for next year's roadmap.

The Takeaway

Almost every coding agent above bundles the same three layers together: which agents you can use, how they're governed, and which cloud they run on. Pick one and you've usually picked all three. The governance layers — JetBrains Central and Port.io — are the clearest sign the market is splitting those apart: control planes that manage whichever agents, models, and clouds you choose. That's exactly the architecture this site argues for: agents, governance, and cloud infrastructure as three independently replaceable layers, not a single vendor's bundle.

The layers underneath make that concrete. A gateway like LiteLLM turns "which model" into a config line and puts one budget and one audit trail under every agent in the org. An open sandbox decides whether execution stays on your infrastructure. An open trace store decides whether the record of what agents did to your code is yours. None of these are exciting purchases; all three are the difference between a stack you can change and a stack you are stuck with. The Secho Quadrant shows why: almost nothing occupies the top-right, so wide coverage and low lock-in are still bought separately.

The Eye Cycle makes the same point about techniques. The two ideas closest to load-bearing — model routing and deterministic rule-based refactoring — are the two that generate the least excitement, and the technique that decides whether any of this is safe to run unattended is not generation at all. It is verification: replaying real traffic and comparing the answers, which is what The Method is built on.

That's the difference between adopting a platform and building the capability yourself. The right platforms above can still be part of your stack — the question is whether your architecture lets you swap any one of them later without rebuilding the rest.
