Token economics

Your codebase is a line item

Refactoring has always lost the funding argument, because its benefit was diffuse and nobody could price it. Agents changed that by accident: they pay to re-read your code on every single task, and that meter is now visible.

11 September 2026 8 min read

A human engineer reads a confusing module once, swears at it, and carries that understanding for the rest of their time on the team. An agent reads it again on every task, pays full price each time, and remembers nothing.

That asymmetry is doing something to your cost base that no invoice will ever show you. It also does something more interesting: it puts a meter on a decision that has resisted measurement for forty years.

The experiment

Giles Edwards-Alexander ran the cleanest version of this test we have seen published. He took a 17,155-line Rust data access layer — one file — and applied fifteen refactoring steps, splitting it across nineteen files. Total lines of code across the project stayed roughly flat at about 49,000. Nothing was deleted. Nothing was rewritten. The code was reorganised.

Then he had an agent implement the same features again, and counted the input tokens.

Files in the data access layer119—
Total project LOC~49,000~49,000unchanged
Cost per task at $3/M input~$0.48~$0.08~40¢ saved

The mechanism is not subtle and that is rather the point: the agent has to read less code to do the same job. A 17,000-line file has to be pulled into context more or less whole. Nineteen well-bounded files can be loaded selectively. Same logic, same behaviour, a fifth of the reading.

Why it works, stated properly

Agents do not accumulate. Every task starts from something close to zero and reconstructs whatever understanding it needs from the source, then throws it away. Where a team's comprehension of a system is a one-off cost that amortises across years of work, an agent's is a per-task cost that recurs forever.

So the thing you are paying for, over and over, is not generation. It is comprehension. And comprehension cost is a function of how much the agent has to read to be confident about a change — which is exactly what module boundaries, clear types and small surfaces control.

Structure used to be a quality argument. It is now a unit-cost argument, and unit costs get funded.

This is worth sitting with, because it inverts a long-standing organisational problem. Refactoring has always been the work that loses. It competes against features for the same engineers, it produces no user-visible change, and its benefit — "maintainability" — has never had a number attached that survived contact with a finance conversation. Every engineering leader has made the argument and every one of them has made it on faith.

The argument now has a meter on it. Not a good meter yet, but a real one.

What this number is not

Three things, and the author is straightforward about all of them, which is why the result is worth repeating at all.

Read the caveats before quoting the 83%

The token counts are approximate. There is no reliable live token counter, so figures were derived from character counts divided by four. That is a standard approximation and it is still an approximation.

The refactor's own cost was not measured. The upper-bound estimate for performing the restructuring was around five million tokens. At the ~132,000 tokens saved per task, the break-even is somewhere near forty tasks — but since the refactoring cost was an estimate and not a measurement, the payback period is genuinely unknown.

It is one experiment, on one codebase, in one language. A monolithic 17,000-line file is close to the worst case, which means 83% is close to a ceiling rather than a typical result. Expect less on a codebase that was already reasonably organised.

So the honest reading is not "refactor everything, it pays for itself." It is: there is now an instrument where previously there was only conviction. That is a smaller claim and a much more useful one.

The trap this creates

A measurable proxy attached to a budget will be optimised, and this one has an obvious bad equilibrium. If you pay per token read, the cheapest move is to make files smaller. That is not the same as making the system simpler, and the two come apart quickly.

You can shard a tangled module into thirty files that all import each other and watch your per-task token count improve, because the agent now loads four files instead of one. You have not reduced the complexity. You have distributed it, made it harder for a human to follow, and bought a metric.

The thing that actually fell in the experiment was not file size. It was how much of the system you must understand to change one part of it — and file splitting was the means, not the end. If your restructuring does not reduce that, the token count will eventually tell you, because the agent will start pulling in the whole dependency web anyway. Watch for the reading cost creeping back up after a reorganisation. That is the signal that you moved the mess rather than removed it.

Who owns this now

If comprehension is billed per task, code structure is an operating expense. That reclassification is the practical consequence, and it changes three conversations.

It changes who funds it. An operating expense with a measurable driver gets treated differently from a quality initiative. The question stops being "can we afford a refactoring sprint" and becomes "what is the ongoing cost of not doing it", which is a question with an answer.

It changes what you measure. We have argued before that the useful unit of AI spend is cost per merged PR, not cost per token. Structure is one of the very few levers that moves that denominator without touching headcount or model choice. Most cost optimisation in this space is a negotiation with a vendor; this one is entirely inside your own control.

It changes what a legacy estate costs you. The parts of your codebase nobody wants to touch are, by construction, the parts an agent will pay the most to read. Agentic coding does not make an unstructured estate cheaper to work on. It makes the cost of that estate recurring, visible, and attributable to whoever is running the agents.

How you would actually know

None of this is visible at the invoice. A monthly total from a model vendor cannot tell you which repository consumed it, and repository is the unit that matters here — it is the thing you can restructure.

What you need is boring and specific: token accounting tagged per repository and per task type, collected at the point the call is made. Then you can do the only comparison that settles anything — the same class of task, on the same repository, before and after a restructuring.

the measurement, minimally
# tag every call at the gateway, not at the vendor
metadata:
  repo:        "billing-core"
  task_type:   "feature"      # feature | fix | review | migration
  run_id:      "a41f…"

# then the question you can finally ask:
# median input tokens per feature task, billing-core,
# 30 days before restructure vs 30 days after

Two honest notes on this. First, you need enough volume for the comparison to mean anything — a handful of tasks either side of a refactor tells you nothing, because task difficulty varies more than structure does. Second, hold the model fixed across the comparison window. A model change in the middle will move input token counts on its own and you will have no way to separate the two effects.

And if your AI spend is small enough that nobody has asked where it goes, none of this is worth building yet. Measure it when the number starts mattering, not before.

If you take four things
  1. Agents do not accumulate understanding. They re-read and re-pay on every task, which makes comprehension a recurring cost rather than a one-off one.
  2. One measured experiment cut input tokens 83% by restructuring alone, with LOC unchanged — but its payback period was not measured, so treat it as an instrument, not a mandate.
  3. Do not optimise file size. Optimise how much of the system you must understand to change one part of it. The first is a metric; the second is the thing.
  4. Structure is one of the only cost levers entirely inside your control. You cannot see it at the invoice — it needs per-repository accounting at the call.
Running this in production

The software is free. The operation is the work.

Per-repository token accounting is a gateway feature, and LiteLLM does it out of the box — open source, yours to run, an afternoon to stand up. What takes longer is making it something finance and engineering will both act on: a tagging convention that survives contact with real teams, retention that satisfies a security review, high availability so the gateway is not a new outage class, and a reporting cadence that lands before the budget conversation rather than after it.

Revolgy runs it as a managed service in EU regions — deployment, SLA-backed operation, model policy, and monthly attribution reporting, with metadata processing set out explicitly in the DPA. We process call metadata, not payloads: that answers the commercial questions and not much else, which is deliberate. You keep the open-source software and the exit path; we carry the pager.

Two limits worth saying plainly. Below roughly a five-figure monthly spend, a governed gateway is not worth the operational weight — keep it simple until the number matters. And putting every call through one path makes that path a single point of failure, which is a real trade and the reason the availability work is the expensive part rather than an afterthought.
