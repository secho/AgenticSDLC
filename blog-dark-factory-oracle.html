Verification

A dark factory needs an oracle, not a bigger model

Shipping code no human has read is easy for about four months. The question was never who read it — it is what “verified” was doing in that sentence.

11 September 2026 10 min read

A dark factory ships code that no human has read, verified only by other machines. Most of the argument about whether that is reckless is spent on the wrong half of the sentence. The interesting half is the second one.

The term is borrowed from manufacturing, where it is literal: the lights are off because the only things on the floor are robots, and robots do not need to see. FANUC has run plants like that since 2001. The software version turns the diff into the factory floor — nobody wrote it by hand, nobody reviewed it, nobody read it before it shipped.

What a dark factory actually is

The framing comes from Addy Osmani's Software Factories, Light and Dark (July 2026), and it is worth being clear about what he does with it, because the phrase has escaped the essay and is being used to sell things the essay argues against.

Osmani is not recommending the dark factory. He is describing it carefully in order to say where it fails. His charge is comprehension debt — the widening gap between how much code exists and how much any human still understands — and his line about it is the one worth keeping: a dark factory does not pay that debt down, it takes it on as fast as it can, with the tests green the whole way. His prediction is not a catastrophe. It is that the reckoning arrives quietly and late.

His evidence is one reported experience: Dex Horthy running a fully automated pipeline for about four months with nobody reading the code, and a failure that took painstaking manual debugging to locate. That is a single case, reported second-hand, not a measurement. The same applies to the rule of thumb that gets quoted alongside it — that an agent holds up for three to ten steps and starts losing the thread past twenty. Both are worth knowing. Neither is a number you can plan against, and treating them as findings does the argument no favours.

What Osmani actually lands on is not a verdict on darkness but a job description: the skilled work is deciding, loop by loop, where the light switch goes. All dark and you are dismantling the thing four months later. All lit and nobody can get a review done. Our disagreement with him, such as it is, is narrow — it is about what counts as evidence that a particular switch can be flipped, and we think that question has a more mechanical answer than he gives it.

The one thing everyone agrees on

Generation is cheap. Acceptance is not. Osmani puts it as verification rather than generation being the real constraint on a factory; we have been putting it as an agent being able to write a replacement in a minute and unable to tell you whether you may deploy it. Same sentence, arrived at from opposite ends.

This is now consensus among people who have run this work at scale, and we no longer claim it as a distinctive finding — it is the premise, and the rest of this post is what follows from it. If you want the claim in its original form it is cited on the approach page, where it belongs to Osmani rather than to us.

Your estate is already dark

Here is the part that tends to go missing. A dark factory produces code that ships without human comprehension. Most large organisations already own a very large quantity of exactly that.

Ten thousand stored procedures, accreted over fifteen years, written by people who have left, with no documentation and no tests. Nobody has read them in a decade. They run the business. That is code shipped and maintained without human comprehension — it simply took fifteen years and a payroll to produce it, so nobody thought to call it a factory.

The dark factory does not introduce unread code. It manufactures it faster.

This changes the question. If comprehension debt were only a risk you might take on in future, you could decline it. It is not: it is the opening balance on most legacy estates. And it now has a running cost attached, because an agent re-pays for comprehension on every single task rather than accumulating it the way a team does. The parts of the estate nobody understands are, by construction, the parts an agent pays most to read.

So the practical question is not whether to allow unread code into existence. It is what you are able to prove about the unread code you already have, and what that permits you to automate.

What a loop has to prove

Osmani's test for full autonomy is a good one, and we would not change it: the check has to be cheap, run at high frequency, rely on something that cannot easily be faked, answer immediately, and not drift over time. Green-or-red oracles qualify. Type gates qualify. A review agent with a real rubric qualifies.

The difficulty is that most codebases cannot answer it. A fifteen-year-old procedure has no types worth the name, no seams, and no test suite — and the architectural safety net Osmani recommends, the types and boundaries and dependency injection, is exactly what you cannot retrofit into it this quarter. That is not a criticism of his prescription. It is a statement about which codebases it reaches.

For an estate like that there is one oracle available, and it is already running: the incumbent implementation. Record what production actually does — arguments, returned rows, the full set of rows written — and those recordings become the test suite. It is cheap, it runs per call, it answers immediately, and it is hard to fake because nobody authored it. Hand-written tests encode the author's model of the system, which is precisely the artefact that left the company in 2016. Recorded traffic encodes what the system does, in the proportions it does it, including the states nobody would have thought to construct.

The switch is decidable

This is where we would push past Osmani rather than paraphrase him. He gives criteria for what earns the dark. He does not give a procedure for deciding it per artefact, and at ten thousand procedures the difference between a criterion and a procedure is the whole job.

The procedure is a first pass that reads for verifiability rather than for meaning. For each procedure it answers one question: what class of evidence could, even in principle, establish that a replacement behaves identically? The answer is a property of the code, decidable by static analysis, not a matter of opinion — and it sets a hard ceiling on how much autonomy anything can ever be given over that procedure.

Note the last row, because it is the one that does not move. A procedure that reaches outside the transactional boundary cannot be verified this way at any model capability. Better models do not change it; it is a property of what can be observed, not of what can be reasoned about. Whatever else gets automated, that class keeps a person on it permanently.

This is the same instinct as matching agent freedom to task risk, with one improvement: risk is a judgement someone has to make and defend, while verifiability class is mechanical, cheap, and total. It should never be sampled. Run it across the whole estate, because it is the pass that decides everything afterwards.

What honest dark looks like

On a real procedure, the verdict run looks like this: 2,190 recorded cases replayed against the replacement, 2,178 matching on both the returned rows and the full intended write-set, twelve differences routed to a person with the evidence attached. The customer sees only the incumbent's answer throughout; the replacement runs inside a transaction that is always rolled back.

Nobody read 2,178 diffs. That is genuinely lights-out, and it is more than the nightly lint-fix cron that usually gets offered as the safe example of unattended work. But it is only worth anything if the machinery doing the accepting is itself under measurement, and this is the part that gets skipped.

Green tests are not evidence

The dangerous failure of an automated pipeline is not a red build. It is a suite that passes while checking less every month. Three numbers catch it, and none of them is optional if the pipeline runs unattended.

Baseline divergence. Replay the recorded traffic against the incumbent, before replacing anything. The answer must be zero. If the old code cannot be shown to match itself, every later verdict inherits that noise as an error bar and none of them carry information.

The normalisation surface, and its trend. Every field you quotient out to suppress false differences — a timestamp, a generated id, a floating-point tail — is a field on which nothing is being checked. A growing normalisation set is the leading indicator of a migration drifting toward agreement that means nothing. Track the count, not just the contents.

Audited classifier false-negative rate. Something has to label the thousands of raw differences as noise or as real change, and its false negatives are the only silent failure in the whole method: a false positive costs a reviewer five minutes, a false negative ships a behaviour change with a certificate saying it did not happen. Sample the noise bucket by hand every run and publish the rate. An unaudited classifier has an unknown error rate, and an unknown error rate is not evidence.

Which turns the acceptance of a dark run into something publishable rather than something asserted:

acceptance recordper procedure
# publish this, or the verdict is an assertion rather than a result
trace:                "18,442 calls / 14 days -> 2,190 distinct cases"
baseline_divergence:  0        # incumbent vs itself. non-zero = error bar on everything below
branch_coverage:      71%      # the other 29% is unverified, not passing
normalisation:        6        # fields quotiented out, each justified. the TREND is the metric
classifier_fnr:       0.4%     # from audited sampling. unmeasured = unknown = not evidence
adjudicated:          12       # each with decision and rationale recorded

Every line there is a number somebody can disagree with. That is the point of it. The technical brief sets out the normalisation taxonomy and the instrumentation in full, including what each normalisation costs you in strength.

What the dark cannot reach

A method that claims no limits should not be believed, and this one has a hard structural ceiling that no amount of model improvement moves.

The replacement is derived from the incumbent — through the specification, and often by a model that read the original directly. Their errors are not merely correlated; shared error is the design intent, because preserving behaviour is the whole objective. Classical N-version programming assumed independently written implementations fail independently, and Knight and Leveson refuted that assumption forty years ago. Here it is not even assumed.

A shadow run detects divergence, never shared defect.

So machine verification of this kind can tell you that nothing changed. It cannot tell you that anything is right. That is a real bound on what "verified only by machines" is ever going to mean, and it is why the guarantee is stated as behaviour preservation rather than correctness.

Three more, briefly, and then the one the site has not said before.

Some work stays lit regardless of the metrics. Changes that are irreversible and unverifiable at the same time — schema migrations against a live core, anything with accounting or regulatory consequence — fall outside rollback-and-compare entirely, because you cannot take the observation without committing it. Those remain with people not because a model could not attempt them, but because the cost of being wrong is out of all proportion to what automation saves. The rest of the limits are set out here.

A permanent comparator costs money forever. Keeping the shadow run going after cut-over is the single change that most widens what agents can be trusted to do unsupervised, and it is duplicate compute indefinitely plus the standing cost of maintaining the normalisation set and auditing the classifier. Below a certain estate size that does not pay, and you should say so out loud rather than discover it in a budget review.

And the one that matters most here: a green verdict run preserves behaviour without restoring comprehension. On the procedure we use as the worked example, a status code has been excluded from a calculation since 2011 and nobody knows why. The migration reproduces that exclusion deliberately — preserve behaviour, do not fix bugs, or the comparison stops distinguishing "the new code is broken" from "the new code is better". The replacement passes. Nobody understands it any better than they did. Osmani's comprehension debt survives a successful migration completely untouched.

This method pays down change-risk debt: it makes an estate safe to modify. It does not pay down comprehension debt, and anyone selling it as though it does is overselling it. The two are different balances and only one of them is being serviced.

Where the lights go

Osmani's closing move is that the person never left the factory, they moved — up from the line to the end of it, designing the thing and guarding the gate. We would add the operational half: the gate has a width, and you can measure it.

Twelve adjudications out of 2,190 cases is a number. It goes up when the instructions are wrong and down when they are right, and it is the same measurement whether the work is a migration or anything else an agent runs unattended. The intervention rate is the one metric here that is meaningful without a baseline, and it is what should gate expansion. You do not widen what agents may do on their own because a vendor shipped a better model. You widen it because the intervention rate in the current scope fell and stayed down.

Which is also why we still have fully unattended ticket-to-PR sitting in the reckoning phase rather than the plateau. The capability is real and the demos are honest. What has not held is the economics at organisational scale, and the cost that bites is not inference — it is senior review time spent on plausible-looking output. Dark arrives as a governed subset of work that earned it, procedure by procedure, not as the default intake path.

Turn the lights off where a machine can prove the thing. Leave them on everywhere else. The skill is knowing which is which, and that turns out to be a question about evidence rather than a question about ambition.

If you take four things
  1. “Verified only by machines” is a claim about the verifier, not about the code. Interrogate the verifier.
  2. Which loops may run dark is decidable mechanically, by what evidence could ever establish equivalence — and one class can never run dark at any model capability.
  3. Baseline divergence, normalisation surface and audited classifier false-negative rate are what separate an honest dark run from a green suite that checks nothing.
  4. A passing migration preserves behaviour without restoring understanding. Comprehension debt is a separate balance and nothing here services it.
Running this in production

The harness is the work, and it is nobody's full-time job

Everything above depends on machinery that has to be built once and then kept honest: recording production traffic without perturbing it, maintaining the normalisation set and justifying each entry, sampling the classifier's noise bucket often enough that the false-negative rate is measured rather than assumed, and keeping the comparator running after cut-over so distribution shift shows up as divergence instead of as an incident.

None of that is exotic and none of it is a product. It is ordinary operational discipline applied to a component that usually gets stood up for one migration and then quietly becomes the thing your autonomy budget rests on. Revolgy runs it as an operated service: the replay harness, the normalisation set under review, the audit sampling, and the acceptance record published per procedure so the evidence outlives the engagement.

Two limits worth stating before anyone signs anything. The comparator is duplicate compute for as long as you run it, so below a few hundred procedures the arithmetic usually does not work — do it by hand and spend the money elsewhere. And we do not adjudicate divergences. The system surfaces them with evidence attached; deciding whether a fifteen-year-old behaviour was intentional is a question about your business, and it stays with your people.
