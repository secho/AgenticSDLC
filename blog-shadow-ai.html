Shadow AI is a routing problem, not a policy problem

People paste source code into consumer chat windows because the sanctioned path is slower, or absent. Blocking does not remove the demand — it removes your visibility of it.

28 July 2026 8 min read

Every organisation that has surveyed this honestly has found the same thing: a substantial fraction of employees use AI tools the company has not sanctioned, and a meaningful fraction of those have pasted internal material into one. Developers are not the worst offenders, but they paste the most sensitive material — source code, stack traces with credentials in them, production data used to reproduce a bug.

The standard response is a policy and a block. Both are reasonable. Neither works, for a reason worth stating plainly.

Why blocking fails

Shadow AI is not a discipline problem. It is a latency and friction problem wearing a discipline costume. The person pasting a stack trace into a consumer chat window is not defying policy for entertainment; they are solving a problem in the fastest way available to them. If the sanctioned path requires a ticket, a two-week approval, and a model that is a generation behind, the unsanctioned path wins every single time, and it wins on merit.

Blocking then produces a predictable sequence:

  1. The corporate domain is blocked on the corporate network.
  2. Usage moves to personal devices, personal accounts, and phone tethering.
  3. The same data leaves, in the same volume, now with no log, no retention control, and no way to answer a regulator's question about where it went.

You have not reduced the risk. You have converted a visible, governable risk into an invisible, ungovernable one, and you have done it while believing the opposite.

The block does not change the behaviour. It changes whether you can see the behaviour.

The reframe

Treat it as a routing problem: make the governed path the fastest path, then the routing decision makes itself.

This inverts what the security control has to achieve. It is no longer "prevent people reaching model vendors" — a losing proposition against any determined user with a phone. It becomes "ensure the easiest available route to a good model happens to pass through something we operate". That is winnable, because you control the thing that determines convenience: the default configuration on every developer machine.

Three properties decide whether the governed path wins:

  • Model parity. If the sanctioned models are visibly worse, people route around them. This is the requirement that most internal AI platforms fail. A gateway carrying current frontier models removes the main honest reason to defect.
  • Zero friction at the point of use. Two environment variables, already set, is the bar. Any per-request approval loses to the consumer product instantly.
  • No new credentials. If getting access means a ticket, the ticket is where adoption dies. Provision on the existing identity, as part of onboarding.

Meet those three and shadow usage collapses on its own, because the governed path is genuinely more convenient. Miss any one and you are back to enforcement, which does not work.

What the governed path buys you

Once traffic is routed through something you operate, several problems become tractable that were previously not:

ControlWhat it doesWhat it does not do
model allowlist Restricts which models and vendors can be reached, per team Nothing about what is sent to permitted ones
secret redaction Strips detected credentials and key patterns before egress Catch everything — it is pattern matching, not comprehension
audit log Records who called what, when, at what cost Require payload retention — metadata is enough and usually preferable
regional routing Pins processing to chosen jurisdictions, with evidence Help if the vendor sub-processes elsewhere — check the contract
per-team budgets Caps spend before it is incurred, not after Distinguish valuable from wasteful spend on its own

The regional routing row is the one that most often turns a nice-to-have into a purchase. Consumer and edge-routed services are typically distributed across a global network for latency — excellent engineering, and disqualifying if you need to state which jurisdiction processed a given request. A gateway you deploy in a region you chose can answer that question with a log line.

A note on regulatory framing

It is tempting to sell this on the EU AI Act. Be careful and be current: the Digital Omnibus that entered into force on 27 July 2026 deferred the high-risk obligations (Annex III) from August 2026 to December 2027, with Annex I moving to August 2028. Most Article 50 transparency duties did begin in August 2026.

So the honest framing is not "you are non-compliant today". It is that the deadline moved because the tooling was not ready, evidence can only be collected from the point you start logging, and you now have a defined window to build the record rather than a scramble. Anyone claiming an emergency here will be corrected by your counsel, and will deserve it.

The data boundary, stated precisely

This is where deployments succeed or die in regulated accounts, so it is worth being exact rather than reassuring.

A gateway can log full prompts and responses. In most environments it should not. The distinction that matters:

  • Metadata — who called, which model, how many tokens, how long it took, what it cost, which session. Sufficient for attribution, budgets, capacity planning and audit. Low sensitivity, defensible to retain.
  • Payload — the prompt and completion. Useful for debugging and evaluation, and it is your source code and potentially customer data sitting in a log store, inheriting every obligation attached to it.

The workable default is metadata retained, payloads not retained, with payload capture available as a deliberate, time-boxed, consented exception for a specific debugging need. Put that in configuration, put it in the data processing agreement, and make sure the sentence "we process metadata for cost attribution and operational purposes and do not retain payload content" is literally true of the deployment. It is the sentence that gets you through security review.

The failure mode to design for

A gateway on the critical path is a single point of failure for every AI-assisted workflow in the organisation. When it degrades, every developer, every agent, and every automated pipeline that depends on a model degrades with it — simultaneously, and during working hours.

This is manageable, and it must be managed explicitly:

  • Run it multi-zone with health-checked failover. A single instance is a demo.
  • Configure vendor-level fallback so one provider's outage is not yours.
  • Document a break-glass direct-to-vendor path, with the reduced controls it implies stated in advance, so the decision is not made under pressure.
  • Monitor and alert on it as a tier-one dependency, because that is what it is.
  • Rehearse the upgrade path. Gateways move fast; an upgrade that interrupts every agent in the company is an outage you scheduled yourself.

None of this is exotic. It is ordinary operational discipline applied to a component that is often installed as a side project and then quietly becomes load-bearing without anyone deciding it should.

If you take four things
  1. Blocking converts a visible risk into an invisible one. It does not reduce it.
  2. Model parity, zero friction, no new credentials — miss any one and the governed path loses.
  3. Retain metadata, not payloads, and make that boundary explicit in configuration and contract.
  4. Anything on the critical path needs multi-zone operation and a documented break-glass route.
